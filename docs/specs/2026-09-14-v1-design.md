# claw-chat V1: local project and decision workspace

Status: **Product specification approved by the project owner on September 14, 2026 at 23:20 America/Los_Angeles.** The standalone companion, managed-stage boundary, V1 scope, and proposed MIT license are approved. Detailed visual direction is under discussion; implementation planning proceeds from this specification.

## Purpose

Give an individual OpenClaw operator a local workspace for large jobs: inspect conversations and delegated work, curate reusable project context, and review consequential decisions before starting dependent stages.

The central workflow is:

1. Select messages in a chat and create a short-term or long-term context project.
2. Curate a small source-linked context packet for a bounded job.
3. Run independent tasks within a stage and inspect their execution trees.
4. Review the stage's evidence, proposed decisions, assumptions, and missing information.
5. Approve a specific revision before explicitly starting the next dependent stage.

Success means a human can identify which context a task received, which result supports a decision, and what work is waiting on that decision. V1 does not claim to eliminate hallucinations or verify private model reasoning.

## Prior art and existing overlap

Research checked on September 14, 2026. These are documentation/repository claims, not a hands-on certification of competing products.

- OpenClaw's public Control UI documentation already describes chat, multi-agent navigation, child task inspection, and live activity. Its chat documentation describes subagent transcript readers with earlier-history loading. We should reuse supported runtime interfaces rather than sell a tree viewer as an unprecedented feature.
- OpenClaw's current Sessions and Sidebar documentation explicitly describes parent/child navigation and forks. The installed release and current upstream documentation can differ; support must be tested rather than inferred from the current website.
- Existing OpenClaw task and approval interfaces provide useful runtime state. Reuse those supported interfaces rather than treat transcript text as an authoritative execution ledger. Native tool approvals and app-owned stage reviews have different authority.
- Use the established workflow pattern of bounded stages and explicit approval gates. Keep execution lineage, dependency edges, and context provenance distinct.

## Approaches considered

### A. Read-only companion

Browse chats, child trees, and local context projects. Lowest integration risk and fastest initial release. However, decisions are annotations only; it does not satisfy the checkpoint requirement by itself.

### B. Local companion with explicitly managed stages — recommended

Add app-owned project context and a small, durable stage controller. Each stage comprises a fixed set of user-reviewed tasks. Approving a stage makes its successors eligible; a separate explicit action starts them. Existing sessions remain observable but unmanaged. This makes the enforcement boundary visible and avoids pretending to pause arbitrary running agents.

### C. Core fork or deep orchestration plugin

Potentially intercepts arbitrary agent work and governs it mid-run, but expands the permission surface, upgrade burden, and failure modes. Defer until the narrower workflow proves useful. Do not modify an operator's Gateway or require weakened safeguards for V1.

## V1 scope

### 1. Connect and inspect

- Desktop-browser application served by a local process, bound to loopback only.
- One Gateway per app instance; one human operator. No cloud accounts, public hosting, remote control, or team permission model.
- Explicit connection and session selection. No automatic ingestion of every local conversation or memory file.
- Read-only inspection is the default; enable managed execution separately and show the scopes it needs.
- Session list, chat transcript, expandable tool calls, and nested child-run explorer.
- Show unavailable, truncated, stale, or unlinked data explicitly. Missing cost is unknown, not zero. Never invent parent edges from similar titles.
- Existing channel conversations are inspection-only in V1. Chat submission and task launch target explicitly selected app-owned sessions; no accidental replies into messaging channels.
- Use source-reported model/usage/status when available. Token usage is not an accuracy score.

### 2. Create context projects from chat

Select one or more messages, then choose **Create project** or **Add to project**. Review the exact excerpts before saving.

Project lifetime is independent of activity status:

- `short_term`: bounded effort; archive on completion after user confirmation.
- `long_term`: ongoing body of context; retain until explicitly archived or removed.
- `active` / `archived`: availability, separate from lifetime.

No automatic deletion based on lifetime. Promoting a short-term project to long-term does not rewrite its history.

Context items have explicit kinds: source excerpt, note, constraint, assumption, proposed decision, approved decision. A transcript excerpt is evidence of what was said, not proof the statement is true.

Keep source references, excerpt hashes, capture time, and author/source labels where supplied. Do not infer human identity from model speaker labels. A later source becoming unavailable does not silently replace the saved excerpt.

Users curate context manually in V1. No background model summarization, embedding service, cross-project search, or automatic harvesting of private memory.

Before launching a task, preview the selected packet and its size. Store an immutable snapshot and digest. Each task records the exact snapshot it received. This packet is only claw-chat's contribution to the prompt; the Gateway may add its own system instructions and memory. Never label it as the model's complete context.

### 3. Managed stages and checkpoints

V1 supports fixed, ordered stages with several independent tasks per stage. It is not a general-purpose workflow designer. Parallelism is bounded by a user-visible cap and the Gateway's own limits.

Each task has an objective, acceptance criteria, context snapshot, dependencies through its stage, and a source-linked result. Human-reviewed inputs are required before dispatch; a model cannot add arbitrary stages or launch dependent work through claw-chat itself.

Dispatch creates fresh app-owned sessions through the supported session-creation API, then sends each task with a stable idempotency key. These are **claw-chat managed tasks**, not necessarily native OpenClaw subagents. A native child spawned within one is separately labeled and correlated through runtime metadata. Do not fabricate native parentage by merely setting a label or drawing an edge.

A checkpoint contains:

- Proposed decision and revision.
- Evidence links and outputs examined.
- Assumptions, missing evidence, and rejected alternatives, entered by the operator or clearly marked as agent-proposed text.
- Exact dependent stage(s).
- Approve, request changes, or reject controls.

A runtime success status alone does not constitute acceptance. All task results must be accounted for before approval. A failed, cancelled, missing, or ambiguous result blocks the normal path; partial results require an explicit revised scope and a new review.

**Enforcement promise:** claw-chat will not dispatch the next app-managed stage until the exact current checkpoint revision is approved and the operator explicitly starts that stage.

**Non-promise:** this does not suspend a model halfway through inference, stop arbitrary pre-existing OpenClaw subagents, undo completed tool side effects, or police everything an already running task can do. Existing Gateway tool policies and approval systems remain in force. Do not describe a checkpoint as a sandbox or a substitute for those policies.

App-local review decisions are not runtime exec/plugin approvals. V1 leaves those runtime approvals in OpenClaw's existing approval interface and never resolves them automatically or asks for approval-management scope just to render the review queue. If runtime approval handling is added later, it must resolve the actual request ID, honor expiry and offered choices, and use a visually separate control.

Nested subagents within a stage may be visible where the runtime exposes them, but they are not independently schedulable gates in V1. A checkpoint is not ready until the stage's known work is terminal. Where descendant completion cannot be established, mark it unresolved and require reconciliation rather than asserting the entire tree finished.

Approval is a local durable operator record, never inferred from text such as 'approved' in a transcript. Agent content cannot call the human approval endpoint. Approvals are bound to the stage revision and context snapshot. A material edit invalidates pending approvals. Already-running work retains its old snapshot and gets a stale-context warning; no silent prompt patching or automatic restart.

### 4. Demo and distribution

- Synthetic demo mode works without a Gateway or API keys and cannot contact a real Gateway.
- Original application code: propose MIT licensing; preserve dependency notices.
- Use only explicitly MIT-licensed Untitled UI components and compatible open-source dependencies, never paid source/components in the public repository. Build custom product views from licensed primitives.
- Initial release through GitHub with source-install instructions and a release artifact verified from a clean environment. npm registry publication is optional later and must not be advertised before ownership and installation are tested.
- No telemetry, external fonts, remote image loading, or automatic update calls in the app. Dependency installation still downloads packages, and agent execution still follows the operator's configured model providers. 'Local app' does not imply local-only inference.

## Interface

A compact desktop workbench with light and dark themes, restrained semantic colors, keyboard support, and no decorative dashboard charts.

- Left: project list and linked conversations; lifetime and archive filters.
- Center: project tabs — Chat, Runs, Decisions, Context.
- Right: inspector for the selected task, excerpt, decision, or snapshot.
- Decisions view: queue of reviews, visible affected stages, and separate approve/start actions.
- Runs view: stage progress and expandable execution lineage. Dependency edges have a distinct visual treatment from spawn edges.
- Narrow screens: switch panels instead of squeezing three columns; full desktop graph editing is out of scope.

Task status is both text and color. Empty states explain how to connect, create a project, or start a demo. Errors retain the last known state with its timestamp. Transcript rendering is virtualized/bounded, preserves reading position, and never executes tool results or embedded HTML.

## Proposed architecture

```text
Browser on loopback
  | authenticated same-origin HTTP + event stream
Local TypeScript service
  |-- project/context/checkpoint SQLite database
  |-- bounded stage dispatcher and reconciliation
  |-- validated Gateway adapter (server-side credentials)
  |-- synthetic demo adapter
  |
OpenClaw Gateway through supported authenticated interfaces
```

- React, Vite, strict TypeScript, Tailwind, MIT-only Untitled UI primitives.
- Node.js local service and SQLite for app-owned state, migrations with tested rollback.
- One local app process owns execution admission. No distributed scheduler, queue broker, hosted database, or background daemon installation.
- Gateway adapter separates feature availability from UI. Unsupported controls are disabled with an explanation. Use supported public packages where compatible, not internal hashed distribution modules.
- Current public client documentation recommends exact `@openclaw/gateway-client` and `@openclaw/gateway-protocol` pins at `2026.8.1`; this is a compatibility candidate, not a claim that this is the latest release or that it works with every wire-v4 Gateway.
- Source inspection of an installed `2026.7.1-2` snapshot found differences from current public docs in history cursors, lineage fields, model mutation scopes, and send/steer semantics. Initial release targets ONE publicly reproducible, tested client/Gateway pair; older-version support is a separate follow-up unless the same adapter passes its tests unchanged.
- Supported versions are named only after live integration tests. Current public docs alone are not compatibility evidence. If the operator's Gateway is unsupported, demo/read-only capabilities must say so; do not upgrade or restart their installation to make the app work.
- Immutable context snapshots and append-only decision events; UUIDs and UTC timestamps with explicit-zone display.
- Transcript bodies are fetched on demand. Retain only explicitly selected excerpts and managed-run evidence needed for review; no bulk historical mirroring.
- Namespace all source references by Gateway identity and authenticated operator identity. Store session key, session instance ID, message ID, task ID, and run ID separately. Clear active subscriptions/caches on identity change; never join equal-looking IDs across Gateways or resets.
- Distinguish original spawn, current control ownership, and conversation fork lineage. Optional or expiring parent fields do not prove a complete historical tree.

## Durability and failure behavior

- Transactionally claim a stage launch; double-clicks and duplicate requests do not duplicate workers.
- Persist dispatch intent and stable idempotency keys before calling the Gateway.
- A lost response is `unknown`, not `failed`; reconcile using authoritative run/session identifiers before retrying. If that cannot be proven, require explicit operator resolution and do not automatically relaunch.
- Reconnect events trigger reconciliation. Do not assume the Gateway replays every missed event.
- Restart restores projects, approvals, and known runs, but never automatically resumes dispatch.
- Context revision changes mark affected approvals stale. Rejected stages do not start successors.
- Archive blocks new starts without silently killing active runs.

## Security and privacy

Loopback is necessary but not sufficient. Protect against other websites reaching a local service.

- Exact Host/Origin validation, strict same-origin API policy, authenticated browser session, CSRF protection for writes, and no wildcard CORS.
- Random app-local browser credential and human-only approval route; agents receive no credential capable of approving decisions. No credential in URLs, localStorage, database records, logs, or public artifacts.
- Gateway credentials remain server-side and are supplied through an OS secret facility or in-memory input, not copied from unrelated stores.
- Explicit session selection is enforced server-side on reads as well as writes. This is an application disclosure restriction, NOT Gateway-enforced per-project authorization: operator scopes can be broader than the selected sessions. Do not use raw session files as a fallback around a Gateway denial.
- Use the supported device identity/pairing flow with read scope initially and an explicit write-scope upgrade for managed tasks. Do not request admin or impersonate the built-in Control UI or privileged backend identity. If a narrowly scoped origin configuration is required, explain it and obtain separate operator authorization; never broaden origins automatically.
- No arbitrary RPC proxy, filesystem explorer, terminal, attachment execution, Gateway config editor, or built-in auto-approval of runtime tools.
- Treat messages, tool output, filenames, URLs, and imported text as untrusted data. Escape content, deny scripts and dangerous URL schemes, and disable automatic remote resource fetching.
- Public examples, CI fixtures, screenshots, issues, and release artifacts use synthetic material only. Redaction is defense-in-depth, not permission to publish real logs.
- App-owned context storage contains potentially sensitive content. Document local filesystem permissions and the fact that SQLite storage is not automatically encrypted. Export is opt-in with a preview, never automatic. V1 exports a versioned JSON project bundle with selected excerpts/decisions/snapshots, excluding credentials and unselected history; importing arbitrary bundles is deferred.
- Archive is reversible and does not delete data. A separate confirmed local-project removal removes its stored content and index entries, leaves a content-free deletion event, and never deletes Gateway history. Refuse removal while app-managed work is active. Document that filesystem backups, SQLite journals, or prior exports may retain copies; do not claim cryptographic erasure.
- Single trusted local OS user is the V1 boundary; this is not a multi-user isolation product or protection against a fully compromised host/agent with unrestricted filesystem and network access.

## Second-order effects and decisions requiring approval

1. **Companion vs core fork:** recommend standalone; avoid coupling all users to a maintained fork.
2. **Managed-stage boundary:** enforce admission of app-owned stages only; do not promise universal agent control.
3. **Context as durable authority:** keep source, proposal, and approval states distinct; otherwise exploratory chat turns into policy.
4. **Versioned snapshots:** adds storage and review steps, but prevents invisible changes to task premises.
5. **Operator permissions:** do not widen the Gateway's existing access policy to make a feature appear to work.
6. **MIT public release:** use only redistributable code/assets and explicit notices.

Record approved sticky decisions as ADRs before implementation. API/export formats are versioned from the first release. The protocol adapter absorbs upstream differences; domain models do not duplicate OpenClaw's private storage schema.

## Release acceptance

V1 is not shipped until a clean installation can demonstrate:

1. Connect to a tested local Gateway using normal approved device pairing, without weakening authentication or automatically changing configuration. Any necessary narrow origin setup is documented and explicitly authorized.
2. Browse an explicitly permitted conversation and supported child lineage; missing history is visibly incomplete.
3. Select messages, create short-term context, promote to long-term, archive, restart, and recover the same project.
4. Run two independent synthetic tasks in one managed stage; inspect their context and evidence.
5. Show that a dependent stage receives zero dispatch calls before approval AND explicit start.
6. Request changes; prove the previous approval cannot authorize the revised stage.
7. Lose the connection or restart between dispatch and acknowledgement; prove no blind duplicate execution.
8. Demonstrate the managed flow against a safe local Gateway fixture, not only a mocked UI.
9. Pass typecheck, lint, unit/integration tests, browser E2E tests, dependency/license review, and secret scan.
10. Render a large synthetic workload without freezing (target dataset: 1,000 session summaries, 100 visible run nodes, 10,000 transcript messages fetched/rendered in bounded pages).
11. Ship setup, compatibility, security, limitations, contribution, and uninstall documentation plus synthetic screenshots.

## Delivery sequence after design approval

1. Prove adapter contracts and capability detection against an isolated test Gateway.
2. Build domain/storage foundation with test-first project, snapshot, and checkpoint transitions.
3. Build connect, chat inspection, tree, and create-project workflow.
4. Build bounded managed stages, explicit decision queue, and restart/reconnect reconciliation.
5. Perform independent spec and code/security review; run the second-order-effects checklist.
6. Validate in a clean local staging environment, prepare a GitHub release candidate, obtain human smoke-test approval, then publish V1.

Do not publish a static mock or read-only viewer as a checkpoint-capable V1. If the adapter cannot support safe managed execution, report the blocker and ask whether to release a clearly labeled read-only preview instead.
